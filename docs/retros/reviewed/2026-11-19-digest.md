### 1. The open non-blocking questions of the question round reach the pull request

Why: in the runs of #7 and #14, a question recorded as "open, not needed" stayed in the History part of the plan. The executor never reads that part, so the pull request did not carry the question.

Decision: applied.

File: `cstack/guides/resolve-issue/plan.md`, section "The approval gate".

Before:

```text
When non-blocking questions stay open, name them. Say that they will appear in the pull request under the heading "Open questions, not needed for this pull request".
```

After:

```text
When non-blocking questions stay open, name them. Copy each one under `## Non-blocking questions`, word for word, with who it is for. The executor never reads the History part, so a question left only there never reaches the pull request. Say that they will appear in the pull request under the heading "Open questions, not needed for this pull request".
```

File: `cstack/skills/resolve-issue/templates/plan.md`, the comment under `## Non-blocking questions`.

Before:

```text
<phase after-build-questions: the questions raised by the reviews or the briefing that do not stop the pull request, word for word, each with who it is for, or "none". They go into the pull request body under "Open questions, not needed for this pull request", after the user has seen them.>
```

After:

```text
<phase plan: the non-blocking questions of the question round that stay open. Phase after-build-questions: the questions raised by the reviews or the briefing that do not stop the pull request. Each one word for word, with who it is for, or "none". They go into the pull request body under "Open questions, not needed for this pull request", after the user has seen them.>
```

### 3. A default about another tool, another command or two processes is never obvious

Why: in the run of #18, a default about a lock that could not be read was assumed without asking, and it caused a race between two processes. In the run of #17, nobody checked what `cstack unit commit` does with an old `green.json`, and two fix commits followed. In the run of #25, nobody read what another tool does with the options it receives, and a blocking question appeared only after the build.

Decision: applied.

File: `cstack/guides/resolve-issue/questions.md`, section "Draft the open questions".

Before:

```text
When a question has an obvious default, do not ask it. Write the default under `## Decisions` as an assumption not asked.
```

After:

```text
When a question has an obvious default, do not ask it. Write the default under `## Decisions` as an assumption not asked. A default is never obvious when it decides what another tool does with a value that the plan passes, what another command does with a file that the change writes, or what happens when two processes run at once. Treat it as a blocking question, and answer it with a test or by reading the code that handles it.
```

### 4. A behaviour and its test go to the same unit

Why: in the runs of #11, #27 and #30, the plan gave a behaviour to one unit and its test to a later unit. The test then passed at once and could never fail first.

Decision: applied.

File: `cstack/guides/resolve-issue/plan.md`, the "Tests" item of "Implementation units".

Before:

```text
- **Tests.** Each unit has either a `Test` line or a `No test` line with a reason. Every new function, route or component starts with a failing test.
```

After:

```text
- **Tests.** Each unit has either a `Test` line or a `No test` line with a reason. Every new function, route or component starts with a failing test. Give each behaviour and its test to the same unit. When an earlier unit already builds what a later unit's test checks, that test passes at once and can never fail first. So never put the negative cases of a command in a last unit of their own: put each one in the unit that writes the code it guards.
```

Decision: applied.

File: `cstack/guides/resolve-issue/plan.md`, the "Files" item of "Implementation units".

Before:

```text

```

## Challenged decision: the model of the implementer

The decision, as written in `cstack/skills/resolve-issue/settled-decisions.md`, sets the model and thinking level of each role in the headers of `agents/`. The implementer runs on Sonnet, with a medium thinking level. The decision says itself that retrospectives showing a faster role repeatedly missing what a later step caught are the evidence for raising that one role.

It protects quality where a miss would ship, and it keeps routine work fast and cheap.

The evidence is strong. Thirteen of the 25 retrospectives say that the implementer wrote the code before the test. Since #25, it even works around the refusal of `cstack unit red` by moving its code aside. Three more retrospectives, #9, #24 and #30, show items that the implementer missed and that a review caught.

Reopening the decision would mean moving the implementer to Opus. That costs many more tokens per unit, and every run has many units. It would also change the comparison that ticket #32 will measure on version 0.3.0. Nothing proves that the model is the only cause. The prompt, the way the plan splits the units (proposal 4) and the missing module (proposal 11) explain part of the cases.

The recommendation was to keep the decision and keep watching it. Proposals 10 to 12 apply first. A `cli` ticket could then make `cstack unit red` refuse when a file of the unit, other than its test, has already changed. That check would no longer depend on the model obeying the prompt. Today the harm is work done twice, not a shipped bug, because red and green already block the commit.

The user's answer: keep Sonnet for the implementer, and keep watching. The next digest should check whether code is still written before the test in most runs. If it is, the next digest should propose to raise the implementer.
