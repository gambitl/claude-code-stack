# Retrospective: #66 — M3-13: Bring back the new commits of a unit that runs a second time in a child worktree

Date: 2026-11-20
Plan file: docs/plans/2026-11-20-66-bring-back-the-new-commits-of-a-unit-that-runs-a-second-time.md
Outcome: done

## Protect

- Before the plan, the advisor reproduced in a temporary repository a case where the comparison by content loses a change and still exits with 0. In that case, a second attempt removes a line, then puts it back exactly as before. That evidence led to the guard of Blocking question 1, and the guard has its own test in `cstack/test/unit/collect.test.ts`.
- The same review found that a cherry-pick onto the same parent, within the same second, recreates the original commit with its hash. The `## Decisions` line "In the tests, the copy of a collected commit must get a hash different from the original" kept the new tests from passing by the clock.
- The independent review added the missing case for a second attempt whose new commit is refused. Its commit is "test(tests): keep the child worktree of a second attempt whose new commit was refused", and the review saw the case fail on the old code.

## Improve

- The plan gave the guard to unit 2, but it also wrote the guard as a general rule in `## Decisions`. The implementer of unit 1 reads that section, so it built the guard too. Unit 2 had nothing left to write, and no failing run of its test could be saved (Executor notes, and the commit "fix(cli): bring back the new commits of a unit that runs a second time" with two `Cstack-Unit` trailers). The failure was only shown afterwards, by removing the guard in a throwaway copy. When a behaviour belongs to a later unit, its `## Decisions` line should name that unit, or the rule should live only in the unit. [skill]
- The first full test run after the rebase had one failed test, and the executor could not say which one, because it had cut the output (Executor notes). The retrospective of #64 reports the same gap. [agent prompt]
- The Review log names commit `ec6ae3d` for the test that the independent review added. The rebase onto `main` gave that commit another hash, so the hash in the plan file is now wrong. Any rebase before the push does the same to every hash written earlier. [skill]

## Trap hit

- The `setup()` helper of `cstack/test/unit/collect.test.ts` forks each child from the current ticket commit. A test that collects right away can then get a copy with the same hash as the original, so a list by hash and a list by content behave alike. It cost nothing here, because the question round caught it before the build.
