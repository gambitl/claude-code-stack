## Ticket

### Why this matters (plain language)

**In plain terms:** Add a command that reads the records of a finished run and says, for each phase and each required command, whether the run did it, skipped it or did it out of order.

- **What the title means**: `cstack audit` is a new command. A run is one execution of `resolve-issue` on one ticket. Its phases are the 15 stages of the skill, such as the plan and the build. Its commands are the `cstack` commands that each phase guide requires, such as `cstack unit red` before the code of a unit.
- **Why we are doing it**: The maintainer asked whether runs really follow every step of the skill. Guards already stop some mistakes, but nobody knows what escapes them.
- **For the user**: After each run, the maintainer sees which steps were skipped. Each skipped step can then get a guard or a clearer guide.

**Goal.** This ticket adds `cstack audit <plan file>`, which checks the phases and the required commands of a run. #90 adds the checks made by helpers and the steps that do not apply.

### Scope

1. Add `cstack audit <plan file> [--home <folder>]` to the manifest, the command list and the README.
2. Find the session files of the run as `cstack measure` does. Reuse its code; do not copy it.
3. Read the tool calls of the sessions. Keep only the shell calls that run `cstack`, and keep their time and their arguments.
4. Check the phases. Each phase starts with `cstack next` and ends with `cstack next --done <phase>`, in the order of `PHASES`. Take the evidence of the five planning phases from the session files only.
5. Check the commands that each guide's block requires, such as `cstack unit red <n>`, then `cstack unit green <n>`, then `cstack unit commit <n>` for each unit. Use the saved test runs and the commits as extra evidence.
6. For each expected step, print one line with the step, "done", "skipped" or "out of order", and the evidence: a time and the kind of record ("session", "run state" or "git").
7. Exit with 0 when every step is done, and with 1 when a step is skipped or out of order. Keep the usual codes for a usage error and an invalid plan.
8. Build every test fixture by hand. Never copy a real session into the repository.

### Acceptance (TDD)

* A new test file for the audit: write first a fixture run where every step happened, and see every line say "done". Then make it pass.
* The same file: a run with no `cstack unit red 2` prints that step as "skipped". A run where `unit green 2` comes before `unit red 2` prints "out of order".
* The same file: when the run state says a planning phase is done but no session shows it, the audit prints that phase as "skipped".
* The same file, negative: the output holds only fixed labels, step names and times. It never holds the text of a session marker, and it never prints a path. Copy the approach of `cstack/test/measure.test.ts` (line 506).
* `cstack/test/manifest.test.ts` counts the new command.
* `npm test` and `npm run typecheck` pass in `cstack/`.

## Code mapping

**Finding the session files.** `measureSessions()` (`cstack/src/measure/sessions.ts`, line 66) does two jobs in one function. Its inner `scan()` (line 131) picks the session files of the run, and `addFile()` (line 123) adds up their tokens. A main session counts when its first and last `timestamp` overlap the window (line 156) and one of its `cwd` values sits in the repository root or in a worktree of the plan (lines 86 to 97 and 158). For each kept main session, it also reads every `.jsonl` file in `<session id>/subagents/` (lines 162 to 167). To reuse this without copying it, the selection part must become its own exported function, which both `measureSessions()` and the audit call. The tests of `cstack measure` (`cstack/test/measure.test.ts` and `cstack/test/measure-worktrees.test.ts`) protect its behaviour during that split. `readLines()` (line 36) parses one JSON object per line and counts the lines it skips.

**The window.** `cstack measure` uses the approval time and the ready time as its window (`cstack/src/commands/measure.ts`, lines 54 and 55). The audit cannot reuse that window, because the five planning phases happen before the approval, and the retro and publish phases happen after the ready time. The run state holds a time for every phase that `cstack next` started or closed, so it can give a wider window.

**The plan and the repository.** `readMoments()` (`cstack/src/measure/moments.ts`, line 44) resolves the plan file, finds the repository root with `git rev-parse --show-toplevel` (line 55), checks a version 1 plan with `readPlan()` (line 64), and returns the `Worktree` paths of the units (line 79). It refuses a plan with no approval time (line 75). Its errors are `MomentsError`, whose messages are fixed sentences with no path (line 18). `cstack measure` maps them to exit code 1 (`cstack/src/commands/measure.ts`, line 44). It expands a `~/` worktree path with the real home folder (line 53) and lists the worktrees with `git worktree list --porcelain` (line 48).

**The run state.** `runFolder()` (`cstack/src/run-state.ts`, line 95) is `<common git folder>/cstack/runs/<plan file name without .md>`. `readState()` (line 127) returns `undefined` when the run does not exist, and throws `RunStateError` with a message that holds the path of the state file (lines 134, 140 and 145). So the audit must catch it and print a fixed sentence instead. `createRun()` (line 159) writes the planning phases at the approval time only when the run is created after the approval (line 164). In a normal run, the run state already exists from `cstack next --done ticket --plan <file>`, so the planning phases carry their real times there. They still prove nothing, because the ticket asks for session evidence for them. `cstack next` writes `doneAt` only after the phase's own checks pass (`cstack/src/commands/next.ts`, lines 154 to 167), and it writes `startedAt` only when it prints the guide (line 195). The `ticket` phase never gets a `startedAt`, because its guide is printed before the run exists (line 128). The retro phase keeps only its latest done time, and `isDone()` counts it only when it comes after the done time of `ready` (`cstack/src/run-progress.ts`, line 16).

**The phases.** `PHASES` (`cstack/src/phases.ts`, line 95) lists the 15 phases in order, and `PLANNING_PHASES` (line 117) names the first five. The order of `PHASES` is a straight line: each phase depends on the one before it, except `retro`, which depends on nothing (line 113), and `publish`, which depends on `ready` and `retro` (line 114).

**The saved test runs.** `saveFailingRun()` (`cstack/src/unit-test-runs.ts`, line 31) writes `units/<n>/red.json` with `time` and `startedAt`, and deletes `green.json` first. `savePassingRun()` (line 37) writes `units/<n>/green.json` with `time`. So the run folder keeps only the latest failing run and the latest passing run of each unit.

**The commits of a unit.** `listUnitCommits()` (`cstack/src/plan/commits.ts`, line 20) lists the commits of `HEAD` that are not on the target branch, grouped by their `Cstack-Unit` trailer. It throws `PlanFormatError` when the target branch does not exist (line 26). After the pull request merges, `HEAD` may hold no such commit, so git evidence can be missing for an old run.

**The plan units.** `PlanUnit` (`cstack/src/plan/read.ts`, line 87) has `number`, `test` when the unit has a `Test` line, `blocked` and `worktree`.

**The block of mandatory steps.** `readSteps(text, name)` (`cstack/src/guide-steps.ts`, line 75) returns `{ ok: true, steps }` or `{ ok: false, message }`. Each message starts with the `name` given by the caller (line 34). A step has `line`, `kind`, its text field and an optional `condition` (lines 19 to 22). `CONDITIONS` (line 8) lists the seven conditions. A guide with no block gives an empty list. The fixture guide `cstack/test/fixtures/steps-block/guides/resolve-issue/build.md` uses the three kinds and all seven conditions. Its command steps are `cstack tracker move '<key>' --to "in progress" --tracker <name>`, `cstack unit order --plan <plan file>`, `cstack unit red <n> | each-unit-with-test`, `cstack unit green <n> | each-unit-with-test`, `cstack unit commit <n> | each-unit`, `cstack tracker comment '<key>' --body-file <file> --tracker <name> | each-dependent-ticket` and `cstack next --done build --plan <plan file>`. The placeholders hold spaces, such as `<plan file>`, so a tokenizer must keep a placeholder as one token. The real guides in `cstack/guides/resolve-issue/` have no block yet, because #88 writes them at the same time as this ticket.

**Reading a guide.** `readGuide(packageRoot, skill, phase)` (`cstack/src/commands/guide.ts`, line 25) reads `<packageRoot>/guides/<skill>/<phase>.md`. Its refusal messages hold the list of skills or phases, not a path. `cli.ts` computes `packageRoot` as the folder above `dist/` (`cstack/src/cli.ts`, line 54) and passes it to `guide` and `next` (lines 59 and 61).

**Tool calls in a session file.** A session file of this run confirms what the ticket says. A tool call is an item with `type: "tool_use"` in `message.content` of a line with `type: "assistant"`. A shell call has `name: "Bash"`, an `id`, and the command in `input.command`. The line has a top-level `timestamp` in UTC, such as `2026-11-23T11:59:47.368Z`, and a `cwd`. Commands are often compound, for example `cd <folder> && cstack next --done ticket --plan <file>; echo EXIT $?`, and sometimes start with an assignment, such as `CSTACK_ORCA_WORKERS=off cstack helper start executor`. One answer is written on several lines with the same message id (`cstack/src/measure/sessions.ts`, line 98), so the audit should count each tool call once, by its `id`.

**A new command.** `CommandEntry` (`cstack/src/manifest.ts`, line 18) and `COMMANDS` (line 49) hold the command list. The entry of `cstack measure` (line 68) is the closest model: usage `cstack measure <plan file> [--home <folder>]`, flag `--home`, exit codes 0, 1 and 2. `HANDLERS` (`cstack/src/cli.ts`, line 57) dispatches by the first word, and the usage text of `cstack` lists every built entry (lines 34 to 47). `cstack/test/manifest.test.ts` (line 156) expects 23 built commands, and `README.md` (line 49) says "twenty-three commands".

**Tests that every new command must pass.** `cstack/test/manifest-implemented.test.ts` (line 46) runs each built command with an unknown flag. It expects exit code 2 and the usage line of the manifest on standard error, and it must not see "unknown command". So `cstack audit` checks its arguments before it reads anything. `cstack/test/cli.test.ts` does the same kind of check. `cstack/test/measure.test.ts` (line 545) scans every file in `cstack/src/measure/` and fails on a network module or a `fetch` call, so a new file there must not use one. `cstack/test/fixtures-public.test.ts` scans every fixture for a home path, an email outside the reserved domains and a private host, so the new fixtures use `{{REPO}}`-style placeholders and sample names.

**Privacy tests to copy.** `describe("nothing private leaves the command")` (`cstack/test/measure.test.ts`, line 477) puts a marker in the session fixtures and checks every output line against a list of allowed patterns (lines 478 to 482 and 506 to 515). It also checks that an unreadable file gives a fixed sentence with no path (line 518), and that the home folder is unchanged (line 538).

**Test helpers to reuse.** `cstack/test/helpers/plan-repo.ts` makes a repository with a first commit (`makeRepo()`, line 15) and commits a plan (`commitPlan()`, line 25). `cstack/test/fixtures/plans/full.md` is a version 1 plan with an approval time, a ready time and ten units, half of them with a `Test` line. `cstack/test/measure-worktrees.test.ts` (line 39) copies a session fixture and fills `{{KEY}}` placeholders with real paths.

**Governing decisions.** ADR-RQG-C (`docs/decisions/ADR-RQG-C-expected-steps-of-a-run.md`, line 46) says the reader takes text, never a path, so the audit can read a guide from an older commit. ADR-SIC-B (`docs/decisions/ADR-SIC-B-run-state.md`) puts the run state under the common git folder; `cstack/src/measure/moments.ts` (line 59) carries its `WHY:` comment. Section 10 of the specification rejected an audit that stops a run, so the audit only reports. The epic says no command starts, waits for or messages an agent, so the audit only reads files and runs `git`.

**Risks.** `cstack/src/measure/sessions.ts` was fixed twice for stray files and unreadable folders (commit `3cea4ab`), and once for child worktrees (commit `d9b499b`). Splitting it can break those cases, so its existing tests must stay green without any change to them. `cstack/src/manifest.ts` and `cstack/src/cli.ts` change in almost every command ticket, so a merge with #88 or a later ticket can conflict there, but #88 does not touch them. The shell commands in sessions are free text, so the audit must never print a part of them. Matching a block step with a call must not depend on the manifest of the version that runs the audit, because milestone R2 removes commands that older runs used.

## Architecture

The approach is locked by the ticket and the answers of the question round. The session selection of `cstack measure` becomes its own exported function, which both commands call. A new folder, `cstack/src/audit/`, holds four small modules: the shell splitter, the reader of the calls, the matcher of a call with a step, and the evaluation that turns the guides, the plan, the run state, the calls and git into lines. The command file `cstack/src/commands/audit.ts` reads the inputs, refuses what it cannot use, and prints the lines. No new decision since the question round.

### Question 2: Where and how the audit looks for the call of a step
The worker of #88 found three steps that the drafted matching rule would judge wrongly. First, `build.md` writes `cstack unit collect <n>... --plan <plan file>`, and a run passes one or more unit numbers there. Second, `cstack unit collect` and `cstack plan status` run after every batch, so their earliest call comes before the steps of later units and would show as out of order. Third, `plan.md` and `retro.md` both write `cstack helper start executor --plan <plan file>` and `cstack helper wait <helper id>`, so the earliest call would match the plan phase in both. Its question, through the coordinator: can the audit look for a step only inside its own phase, and take the last call for a step that comes after the units? The recommendation has three parts. One: the audit looks for the steps of a phase only between the close of the phase before it and the close of the phase after it. The window goes past the phase's own close because a guide can list a step after it, such as `cstack helper start executor`, which `plan.md` asks for after `cstack next --done plan` (`cstack/guides/resolve-issue/plan.md`, lines 49 and 51). Two: instead of the last call, every step takes the first matching call that comes after the steps that must precede it. A step after the units therefore takes the first call after the last step of every unit, which is the final `cstack unit collect` or `cstack plan status`. When every matching call of the window comes too early, the step is out of order, with its latest call as evidence. Three: a placeholder followed by `...`, such as `<n>...`, matches one or more words. In a step that repeats per unit, it matches when the unit number is one of them.
- For: the user
- Answer: yes, as recommended, with the three parts above. The user, in the chat, on 2026-11-23.

So every run of R1 to R3 is written by "0.3.2", even though #88, R2 and R3 change the guides. The check catches an upgrade across releases, not a change between two builds of the same version. If nobody decides, the planner keeps the drafted option and the drafted check. Refusal messages about the guides must name the phase file, such as `build.md`, and never the folder given with `--guides`, because the negative criterion forbids a path in the output; `readSteps()` takes the name from the caller (`cstack/src/guide-steps.ts`, line 34).

**A guide with no block (non-blocking, the run can decide).** `readSteps()` returns an empty list for a guide with no block, and an empty block is refused (ADR-RQG-C, "Decision"). Every phase ends with at least `cstack next --done <phase>`, so an empty list always means a guide written before the blocks existed. Today that is all 15 real guides in `cstack/guides/resolve-issue/`, and it stays so if this ticket merges before #88. Without a refusal, the audit would check only the phases and could exit with 0, which looks like a clean run. The recommendation is exit code 3 with a fixed sentence that names the phase, such as "The guide of the phase build has no block of mandatory steps." This adds no export to `guide-steps.ts`. The test uses a fixture guide folder where one guide has no block. If nobody decides, the audit prints only phase lines for that guide, which is misleading.

**No session found (non-blocking, the run can decide).** The planning phases take their evidence from sessions only (AC8, locked by the specification). When the selection finds no session file at all, every planning phase and every command step would print as skipped, which reads as a disastrous run instead of missing data. That case is likely for runs 3 and 4 (AC10, a later ticket): the selection keeps a session only when one of its `cwd` values sits in the repository root or a worktree of the plan (`cstack/src/measure/sessions.ts`, lines 86 to 97 and 158), so copies of sessions from a moved or re-cloned sandbox match nothing. Claude Code also deletes session files older than its `cleanupPeriodDays` setting, 30 days by default; the maintainer's setting is 180. The recommendation is exit code 3 with a fixed sentence, such as "No session file of this run was found.", printed before any step line. The rejected option is to print the lines anyway with a warning, because a reader of the retrospective would see the skipped lines first. If nobody decides, the audit prints everything as skipped and exits with 1.

**Several commands in one shell call (non-blocking, the run can decide).** In the sessions of #86, implementers ran `cstack unit green 1 ... && cstack unit commit 1 ... 2>&1` as one tool call, so both commands carry the same timestamp. Draft answer 3 says "each tool call counts once, by its id", which a planner could read as one command per call. The rule should be: keep each tool call once by its id, across all session files and helper transcripts, then take every `cstack` command inside it. Two steps with the same timestamp are in order when they come from one call in the order of the text, and otherwise count as in order too, because the audit cannot tell them apart. The splitter is written in `cstack/src/audit/`. It splits on `&&`, `||`, `;`, `|`, `&` and newlines, keeps quoted text and heredoc bodies as data, does not split `2>&1`, accepts the `--flag=value` form that `node:util` `parseArgs` accepts (`cstack/src/commands/next.ts`, line 95), and ignores flags that the step does not name, such as `--timeout 9`. A shell variable such as `--plan $P` matches only a placeholder flag, which is optional anyway. A loop such as `for n in 1 2; do cstack unit red $n; done` will not match `cstack unit red 2`, and the README should say so. A package such as `shell-quote` was rejected because `cstack/package.json` has no runtime dependency today.

**The start of each phase (non-blocking, the run can decide).** Scope item 4 says each phase starts with `cstack next` and ends with `cstack next --done <phase>`, but draft answer 7 judges a phase by its close only. `cstack next --done X` prints the next guide and writes its `startedAt` when the next phase runs in the same place, but only prints a message when the place changes between the main conversation and the executor (`cstack/src/commands/next.ts`, lines 191 to 198). There, a separate `cstack next` must print the guide, and skipping it means a phase done without its guide. That is exactly what the maintainer wants to see. The recommendation is to report a phase as skipped when it is closed but has no `startedAt`, for every phase except `ticket`, which never gets one (line 128), and except the planning phases, whose start is the close of the phase before them in the same session call. The order of the start is not checked, because `markStarted()` overwrites the time at each print (`cstack/src/run-progress.ts`, line 62). For `retro`, the audit uses `isDone()` (`cstack/src/run-progress.ts`, line 12), so a retro done only before `ready` is not done. If nobody decides, the audit ignores the start, and the scope item is only half met.

**Drafted answers 2 to 9 (non-blocking).** I agree with them as written, with the additions above. On exit codes, the ticket says "keep the usual codes for an invalid plan". `cstack measure` maps a `MomentsError` to 1 (`cstack/src/commands/measure.ts`, line 44), while `EXIT.invalidInput` is 3 (`cstack/src/manifest.ts`, line 11). I keep 3, because the manifest is the reference and 1 already means "a step was skipped" here. The drafted refusal for a version mismatch uses 1, which fits "refused: a rule said no".

**Tool call shape (checked by reading a session file of this run).** In the main session of this run, all 39 shell calls appear in a `type: "assistant"` line with a UTC `timestamp`, and 36 of them appear a second time in a `type: "api-request-blob"` line with no `timestamp`, the same `id`, and a command prefixed with `cd <worktree> &&`. A reader that takes every `tool_use` item would double the calls and meet a missing time. So the audit reads only `assistant` lines and keeps each id once. The fixtures should include one such blob line to protect this.

**Helper transcripts (checked by listing the sessions of #86).** The sub-agents that the executor started have `spawnDepth: 2` in their `.meta.json` and sit in the same `<session id>/subagents/` folder as the first-level helpers. So `measureSessions()` already reads them (`cstack/src/measure/sessions.ts`, lines 162 to 167), and the split of that function must keep returning them. The selection must keep skipping the `.meta.json` files, which it does by the `.jsonl` filter.

**Refused calls (checked on this run and the sessions of #86).** A shell call that exits with a non-zero code gets `is_error: true` on its `tool_result`, which I confirmed with a failing command of my own. But about 25 of the 65 `cstack` calls of #86 end with `; echo $?` or similar, so the flag is false for them whatever `cstack` did. The same sessions hold the text `cstack unit red <n>` in heredocs and in the bodies of other commands, which confirms that draft answer 3 must exclude quoted text and heredocs. I keep draft answer 3: a refused call still counts, and the README says so.

**Question for the worker of #88 (non-blocking).** The matching rule of draft answer 4 treats a placeholder flag as optional and a fixed-value flag as required. #88 writes the real steps at the same time, and a fixed value that runs do not pass would make every run fail that step. The question, word for word, in English for the Orca coordination thread: "In a command step, write a flag with a fixed value only when a run must pass that exact value, such as `--done build`. The audit treats a flag whose value is a placeholder, such as `--plan <plan file>`, as optional. It requires every flag that has a fixed value." The work of this ticket is correct whatever the answer, because it tests only against fixture guides.

### Open questions and answers

1. Where the audit reads the guides. Blocking question 1, answered.
2. Non-blocking: which session lines belong to the run. Recommended answer: the audit selects the session files with the same code as `cstack measure`, but with a wider window. The window opens at the earliest time of the run state and closes at its latest time, because the planning phases come before the approval and the retro and publish phases come after the ready time. Inside a kept session, every line counts, as in `cstack measure`, so the first `cstack next` of the ticket phase, which comes before the run state exists, is still read. A session that holds two runs mixes their calls, and the audit does not separate them. The README says so. The user accepted it in the chat on 2026-11-23, together with the additions of the advisor's block.
3. Non-blocking: which calls count. Recommended answer: a call counts when a shell call of a session runs `cstack` as a command, even inside a compound command such as `cd <folder> && cstack next --done plan; echo $?`, or after an assignment such as `CSTACK_ORCA_WORKERS=off`. Text inside quotes, inside a heredoc or after `echo` is not a call. `node cstack/dist/bin.js` is not a call either, because it runs a build of this repository, not the `cstack` of the run. The audit never reads the result of a tool call, so a call that `cstack` refused still counts as a call. Each tool call counts once, by its id. The user accepted it in the chat on 2026-11-23, together with the additions of the advisor's block.
4. Non-blocking: how a call matches a step of a block. Recommended answer: the words before the first flag must be equal, and a placeholder such as `'<key>'` matches any word. In an expanded step, `<n>` becomes the unit number and must be equal. A flag followed by a fixed value, such as `--done build` or `--to "in progress"`, must be in the call with that value. A flag followed by a placeholder, such as `--plan <plan file>`, is optional, because the runs often leave it out. The match never uses the command list of the installed `cstack`, because milestone R2 removes commands that older runs used. The user accepted it in the chat on 2026-11-23, together with the additions of the advisor's block.
5. Non-blocking: which steps this ticket lists. Recommended answer: every phase, then every `command` step of each guide whose condition is empty, `each-unit` or `each-unit-with-test`. A step with `each-unit` repeats for every unit of the plan, blocked units included. A step with `each-unit-with-test` repeats for every unit with a `Test` line. The `helper` steps, the `action` steps and the steps with another condition are left out until #90, which evaluates them. The user accepted it in the chat on 2026-11-23, together with the additions of the advisor's block.
6. Non-blocking: the evidence of a step. Recommended answer: a planning phase is done when a session shows its `cstack next --done <phase>` call, and the run state is never used for it. Any other phase is done when the run state holds its done time, which `cstack next` writes only when the phase really closes (`cstack/src/commands/next.ts`, lines 154 to 167). A command step takes the earliest matching session call. When no session shows it, `cstack unit red <n>` and `cstack unit green <n>` fall back to `units/<n>/red.json` and `green.json` ("run state"), `cstack unit commit <n>` falls back to the author date of a commit with its `Cstack-Unit` trailer ("git"), and a `cstack next --done <phase>` step of a phase that is not a planning phase falls back to the run state. The steps of the five planning guides use the session only. The user accepted it in the chat on 2026-11-23, together with the additions of the advisor's block.
7. Non-blocking: when a step is out of order. Recommended answer: a phase is out of order when it closed before the closest earlier phase that closed. A command step is out of order when it happened before the closest earlier step of its block that is done. For a step that repeats per unit, the closest earlier step is the one of the same unit, so units that ran in another order than their numbers are fine. A step after the units must come after the last step of every unit. The audit judges a phase by its close only, because `cstack next` refuses to close a phase whose dependencies are not closed (`cstack/src/run-progress.ts`, line 46). The user accepted it in the chat on 2026-11-23, together with the additions of the advisor's block.
8. Non-blocking: the output. Recommended answer: the phase lines come first, then the command lines grouped by phase. A phase line reads `phase plan: done 2026-11-23T13:20:05+01:00 session`. A command line reads `build: cstack unit red 2: out of order 2026-11-23T14:02:11+01:00 session`. A skipped step has no time and no record. The step is the text of the guide, with `<n>` replaced by the unit number. The time is a local time with its offset, as in the plan header, written by `localTime()` (`cstack/src/local-time.ts`, line 2). Nothing in the output comes from a session or names a path. The user accepted it in the chat on 2026-11-23, together with the additions of the advisor's block.
9. Non-blocking: the exit codes. Recommended answer: 0 when every step is done, and 1 when a step is skipped or out of order. 1 also covers an unreadable session file, with a fixed sentence on standard error, after the lines are printed. 2 is a usage error. 3 is input that cannot be used: a plan file that is missing, invalid or not approved yet, a run that does not exist, a guide file that is missing, or a block that `readSteps()` refuses. This follows `EXIT.invalidInput` (`cstack/src/manifest.ts`, line 11). `cstack measure` maps a plan error to 1 (`cstack/src/commands/measure.ts`, line 44), so the audit maps the same `MomentsError` messages to 3 instead. The user accepted it in the chat on 2026-11-23, together with the additions of the advisor's block.
10. Where and how the audit looks for the call of a step, raised by the worker of #88 through the coordinator. Blocking question 2, answered.
