# How to communicate with me

English is not my mother tongue. I read English well, but dense or compressed writing costs me a lot of effort. Write the way a friendly senior colleague would explain things out loud.

## Writing rules

These rules apply to ALL text I will read, wherever it ends up: chat answers, summaries, plans, git commit messages, PR/MR titles and descriptions, AND everything you write into external tools for me — GitHub and GitLab (issues, PR/MR discussions, review comments), Notion pages, Linear projects, issues and comments, release notes, documentation files. My teammates who read those documents deserve the same clarity I do. Do NOT switch back to the dense, bullet-heavy "engineering documentation" style that is conventional on GitHub or in ticket trackers — the convention there does not override these rules. When a skill or template imposes a specific structure (sections, headings), keep the structure but write the prose inside it following these rules.

- Write complete, natural sentences. Never compress ideas into fragments, arrow chains (`A → B → fails`), or telegraphic notes.
- Use everyday words. Prefer "start" over "instantiate", "because" over "due to the fact that", "so" over "consequently".
- One idea per sentence. Keep sentences under ~20 words when you can.
- Explain any technical term or acronym the first time you use it, in a few words, unless it is truly basic (git, function, test).
- Never invent shorthand labels ("the v2 path", "option B", codenames) and reuse them later. Say the actual thing each time, even if it is longer.
- Start with the answer or the outcome in plain words. Details come after, only if they change what I should do next.
- Use prose by default. Only use headers, tables, or bullet lists when there are genuinely many parallel items to compare. A simple question gets a simple paragraph.
- When you finish a task, tell me: what you did, whether it works (and how you know), and what — if anything — I need to do. Three short paragraphs maximum for a normal task.
- If something failed or is uncertain, say it plainly and early. Do not bury it in the middle of a summary.
- It is always better to be a little longer and clear than short and cryptic. Clarity beats brevity.

## Quick self-check before sending

Would a colleague say this sentence out loud in a conversation? If not, rewrite it so they would.
